The pyramid shape is deliberate: Tier 1 is cheap enough to run on every keystroke, Tier 2 validates every API contract against a real database, and Tier 3 is reserved for the handful of flows where only a real browser can prove the behavior — tab-switch detection and cross-account persistence, in SocMag's case.

2. Tier 1 Deep Dive — Gaussian MLE Math Invariants

mle-service/main.py scores a student's interest vector against a society's ideal persona by treating the persona as the mean μ of a multivariate Gaussian with diagonal covariance Σ = I·σ² (σ = 0.25 by default), then normalizing the student's likelihood against the Gaussian's own peak:

compatibility_score = 100 × pdf(student_vector) / pdf(ideal_persona) mahalanobis_distance = √( Σ ((student_i − ideal_i) / σ)² )

Because the covariance is diagonal and equal in every dimension, these two values collapse to one clean, testable relationship:

compatibility_score = 100 × exp( −0.5 × mahalanobis_distance² )

This is exactly why the suite can assert on round numbers instead of approximate floats:

InvariantProven byWhy it must hold

3. Tier 2 Deep Dive — Atomic Concurrency & Campus-Restricted RBAC

3.1 Zero-Double-Booking: the atomic slot guard

Interview slots are a scarce, shared resource — two students must never be assigned the same physical slot, even if both click "Book" at the same instant. SocMag doesn't rely on a prior SELECT check (which is itself race-prone); the guard is a single atomic UPDATE inside a transaction, in frontend/app/api/slots/book/route.ts:

BEGIN; UPDATE slot_bookings SET application_id = $1, booked_at = now() WHERE id = $2 AND application_id IS NULL -- the entire guard lives in this predicate RETURNING id, slot_date, slot_time, venue; -- rowCount === 0 => ROLLBACK, respond 409 (someone else won the race) -- rowCount === 1 => mark the application Interview_Booked, COMMIT

Note on terminology: the read-side endpoint (GET /api/slots?status=available) exposes a convenience status filter for the UI's slot picker, but the actual concurrency-safety mechanism is the write-side predicate above — Postgres only lets one concurrent UPDATE win the row, so application_id IS NULL can never be true for two requests at once. This is what makes the guard atomic, not the read-side filter.

TC-SLOT-01 / TC-SLOT-02 prove both halves: a slot with application_id IS NULL can be booked (200, status flips to booked), and immediately re-booking the same slot is rejected (409, transaction rolled back, original booking untouched).

3.2 Campus-Restricted Auth & Role-Based Access

frontend/app/api/auth/login/route.ts enforces the @thapar.edu domain with a regex check before any database query runs, then verifies the password with bcrypt.compare against the stored hash, and finally returns a role (student / society manager) that the frontend uses to route into the correct dashboard.

CheckProven byResult
Valid @thapar.edu email + correct passwordTC-AUTH-01200, role returned, routed by role
Non-institutional email domainTC-AUTH-02400, rejected before any DB lookup
Correct email, wrong passwordTC-AUTH-03401

Honest RBAC gap: the login boundary itself is fully tested, but role isolation is only partially covered. PATCH /api/societies/[id] does implement a real ownership check (403 if the requesting manager doesn't own that society) — but it has no automated test at all. The grading routes (POST /api/grades) implement no ownership check in the source, and there is no test exercising cross-manager access either. Treat "RBAC" as verified at the authentication boundary, not yet at the manager-to-manager isolation boundary.

4. Tier 3 Deep Dive — Real-Browser Proctoring & Cross-Account Persistence

Two things in SocMag can only be proven by a real browser, not a mocked request — Playwright is reserved for exactly these:

4.1 Anti-cheat proctoring (TC-E2E-02)

app/student/societies/[id]/assessment/page.tsx attaches real visibilitychange, blur, and focus listeners when the proctored test loads. The test dispatches a synthetic document.hidden = true via page.evaluate and asserts the "Tab switch detected" banner plus a live "1 switches" counter appear — then dispatches real blur, waits 1100ms of real wall-clock time, dispatches focus, and asserts an away-time counter matching /[1-9]\d*s away/. The deliberate real-time wait (not a mocked clock) is what proves the away-duration math itself is correct, not just that the event fired.

4.2 Cross-account, server-side persistence (TC-E2E-03)

After a Non-Tech manager clicks the GREEN grade dot on /manager/grading, the test performs a full page.reload() and re-asserts the dot's background color is still set. This is the one check that can't be faked by React state surviving a soft navigation — a hard reload discards all client state, so a grade still showing GREEN afterward proves it round-tripped through POST /api/grades into Postgres and back out through GET /api/grades. The same spec also logs in as two different real accounts in sequence (student → manager) via a switchAccount helper, proving the booking-then-grading handoff works across a real session boundary, not just within one logged-in user's state.

5. Practical Testing Runbook

5.1 Tier 1 — Unit tests (pytest)

# from the repo root, in PowerShell cd mle-service .venv\Scripts\Activate.ps1 pytest -v

5.2 Tier 2 — Integration tests (Vitest, needs both servers' env config but no servers running)

cd frontend npm run test:integration

Reads DATABASE_URL from frontend/.env.local and talks directly to the dev Postgres database — it does not need npm run dev running, since it calls the route handlers' logic through Vitest, not over HTTP to a live port.

5.3 Tier 3 — End-to-end tests (Playwright; spins up both live servers itself)

# headless, the default used for CI-style runs cd frontend npm run test:e2e # headed: watch the real Chromium window click through each flow npx playwright test --headed # interactive UI mode: step through, time-travel, and inspect each assertion npx playwright test --ui # run just one spec, headed npx playwright test e2e/track-a-assessment.spec.ts --headed

Playwright's own webServer config (frontend/playwright.config.ts) boots both uvicorn main:app --port 8000 and next dev automatically and reuses them if already running — you don't need to start either server by hand first.
