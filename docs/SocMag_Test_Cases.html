4. Manual Validation & Known Coverage Gaps

4.1 Manual Validation Performed During Development

Two behaviors were manually exercised in the browser before — and in addition to — the automated coverage above:

  • Concurrent slot booking. Two browser sessions raced a booking request against the same interview slot to confirm only one request succeeds and the other is rejected, under genuine simultaneous load. TC-SLOT-02 automates the sequential case (book, then immediately re-book) against the same UPDATE … WHERE application_id IS NULL guard, but does not itself issue two requests in parallel — see §4.2.
  • Hard-refresh persistence of a grading decision. After setting a GREEN rubric grade as a manager, the page was hard-refreshed to confirm the grade was read back from the database rather than held only in React state. This check is now fully automated as the final step of TC-E2E-03.

4.2 Known Coverage Gaps

Zero automated coverage: POST /api/events/register — the event-registration endpoint is not called by any Unit, Integration, or E2E test.
Zero automated coverage: PATCH /api/societies/[id] — the society-profile-edit endpoint, including its ownership check (403 on manager/society mismatch), is not exercised by any test.
Partial coverage: POST /api/grades is only tested for its action: "rubric" branch (via TC-E2E-03). The action: "shortlist" and action: "bulkShortlistGreen" branches have no test.
Indirect-only coverage: POST /api/applications, GET /api/applications, GET /api/slots, and GET /api/test-questions are exercised only as a side effect of the Playwright UI flows (TC-E2E-02/03). No Vitest integration test calls these routes directly and asserts on their response contract in isolation — the Vitest fixture helper (frontend/tests/helpers/testDb.ts) deliberately bypasses them with direct SQL inserts for test speed.
Missing negative/permission test: no test verifies that a manager is blocked from grading or shortlisting applicants of a society they do not manage — unlike PATCH /api/societies/[id], the grading routes implement no such ownership check in the source at all, so there is nothing to test yet, and this should be treated as a product gap as well as a test gap.
Race-condition coverage is manual-only: TC-SLOT-02 proves the atomic guard rejects a second, sequential booking attempt; it does not itself send two requests concurrently. The concurrent case was checked manually (§4.1) but has no automated regression test.
